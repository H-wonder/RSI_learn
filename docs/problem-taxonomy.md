# 问题分类（P1–P9）

> 这是我们自己为论文归纳的“能力类型”，不是数据集官方标签。完整标注见 `data/annotation/tasks_to_label.csv`。

## 分类表

| 编号 | 名称 | 一句话 | 典型任务 | 断言信号 |
|---|---|---|---|---|
| P1 | 单工具状态更新 | 只动一个应用，1–3 步 | `sales.update_contact_phone` | 只有 `*_field_equals` / `*_exists` |
| P2 | 多跳检索与隐式 ID | 先查 A 拿 ID，再查 B，最后操作 C | `sales.multi_hop_lookup` | 多个 `*_find_records` / `*_query` + 后续写操作 |
| P3 | 跨应用对账与同步 | 两边数据不一致，以一方为准合并 | `sales.sheets_reconciliation` | 两边同名字段都有断言；有“旧值不能保留”的负断言 |
| P4a | 资格筛选/规则判定 | 判定谁符合条件、是否越过阈值、是否被排除 | `operations.mailchimp_subscriber_sync`、`finance.qb_invoice_from_orders` | 集合/数量断言、`*_exists`、阈值字段 |
| P4b | 分支路由/优先级 | 决定去哪里、走哪条路径、什么优先级 | `sales.zoom_regional_webinar_coordinator`、`support.zendesk_escalation_waterfall` | 收件人/团队/tier/时段断言 |
| P5 | 排除、负选择与冲突消解 | 排除不该做的；按最新/最高优先级选 | `sales.negative_selection`、`sales.recency_selection` | `*_not_*`、总数必须等于 N |
| P6 | 模糊匹配与脏数据 | 名字拼错、格式不一致、空值 | `sales.soft_matching`、`sales.format_ambiguity` | 断言要求规范化后的值 |
| P7 | 时间、日程与资源冲突 | 排会、改期、时区、冲突 | `sales.calendly_reschedule_chain`、`sales.zoom_calendar_conflict` | 日历/会议工具 + 时间字段断言 |
| P8 | 聚合、评分与多因子决策 | 加权、排序、分组、汇总 | `sales.weighted_priority`、`support.zoho_risk_scoring` | 最终字段等于计算结果 |
| P9 | 长链依赖编排 | 5+ 步互相依赖，前一步输出是后一步输入 | `sales.dependency_chain`、`sales.full_sales_cycle_orchestrator` | 工具链长、断言覆盖链上多个应用 |

## 判定顺序

1. 用户请求里有没有直接给实体/字段？没有 → 先考虑 P2。
2. 要跨几个应用？两个以上 → P2 / P3。
3. 有没有 `*_not_*` 或“总数等于 N”？有 → P5。
4. 有没有条件/规则/优先级？有 → P4。
5. 最终动作是什么？创建/更新/发消息/排会 → 对应 P1 / P7。
6. **主类选“最耗步骤、最容易失败”的一步**，其它记为次类。

### P4 子类判定

P4 原来把两类不同能力混在一起，现已拆开：

- **P4a 资格筛选/规则判定**：核心是“谁符合条件”。典型动作是先读规则表/阈值/日期，
  再得到一个集合或状态；典型错误是**集合成员错**（多做、漏做、阈值算错）。
- **P4b 分支路由/优先级**：核心是“去哪里/走哪条路径”。典型动作是按 tier、金额、
  区域、优先级选择收件人、团队、层级或会议时段；典型错误是**目的地/路径错**。
- 两者同时出现时，主类选**消耗步骤更多、断言覆盖更多**的一侧，另一侧记次类。
- 60 题分布：P4a **16** 题，P4b **9** 题，合计仍是 25 题（41.7%）。

次类出现次数：P5 53 次、P1 31 次、P4（未拆）28 次、P2 17 次。次类保留 P4 粗粒度，避免与主类子类混用。

**观察与修订**：

1. **P4 已拆分**：P4a 16 题（26.7%）、P4b 9 题（15.0%），合计仍是 25 题（41.7%）。拆开后可以区分“集合选错”和“目的地选错”，避免 P4 变成万能类。
2. **P4a 是最大子类**：说明“读规则 → 判断谁符合条件”是当前最常失败的能力；P4b 更接近路由/优先级，适合用显式分支结构验证。
3. **P5 是横切约束**：53 次作为次类出现，说明“不能做错”几乎存在于每个任务。论文里应把 P5 作为**约束层**，而不是普通主类。
4. **P1 主类为 0、次类 31**：纯 CRUD 任务很少，通常嵌在 P2/P4 里。P1 保留为“动作层”标签。
5. **P6 主类为 0**：模糊匹配在样本里不突出，可能被 P2 吸收；需要在全量 600 题里再确认。
6. **P7/P9 少**：不代表不重要，而是它们常与 P4/P2 组合出现；论文里要说明“主类 + 次类”的口径。

> 这些结论基于当前 60 题标注；如后续复核发现分歧再更新。
